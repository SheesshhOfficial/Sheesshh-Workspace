Historical plan · 28 October 2026

Retained unchanged for context. Earlier “not verified” statements and daily-limit requirements describe that date, not the current checkpoint above.

1. Navigation and progression

  • Home Play: select the earliest unfinished stage in curriculum order, never merely the last visited game.
  • Explore: display six sequential forts; only Fort 1 starts unlocked.
  • Fort 1: eight named game slots in sequence. MathFly and NumberLineJump are the two implementation targets now; six other games remain locked.
  • Stage selection: four sequential stages per implemented game. Completed stages remain completed when an attempt is retried.
  • Rewards: one star per completed stage and one sticker per completed game. Replays must not duplicate rewards.
  • Fort flag: requires completion of all eight games, so the two-game demo must not award the flag or pretend the fort is complete.

Use the client’s approved fort/game labels; do not invent the six remaining game names. Exact curriculum ordering must be encoded explicitly and checked against the client content.

2. Shared question and attempt rules

  1. Start or retry the current stage with three lives and zero correct answers for that attempt.
  2. Play the question’s spoken explanation; start the ten-second question timer only after narration finishes.
  3. Accept one answer for the active question. A correct answer adds one to the cumulative stage count; the three successes need not be consecutive.
  4. A wrong answer or question timeout removes exactly one life and presents a new question. It does not erase previously earned correct answers within that still-active attempt.
  5. Three cumulative correct answers complete the stage and award its star once.
  6. When lives are exhausted, retry resets the current stage attempt, not already completed stage/game progress.

Question completion, timeout and repeated taps must be resolved once so simultaneous callbacks cannot remove two lives or grant two rewards. Those are acceptance requirements, not existing test results.

3. MathFly

Four sequential stages use the shared three-correct/three-life rules. Answer buttons control a flapping bird. Flight is a visual response to the selected answer, not a collision-based skill test: no collision penalties. Pick day or night randomly once per attempt and retain it through that attempt.

Use the client’s MathFly reference, sprite sheets, DayBG/NightBG and bird video as inputs for review. The MP4 is not automatically an engine-ready sprite animation. Numeric ranges, stage-specific operations and age/syllabus mapping remain unconfirmed.

4. NumberLineJump

Before/after questions with selectable options, four sequential stages, three cumulative correct answers per stage, three lives per attempt and the same question-timer/narration behavior. Number ranges, distractors and difficulty progression need curriculum confirmation; do not inherit COD’s 1–20 range without approval.

5. Instructions, narration and language

Show an instructions popup on first use and provide an i button on Home and gameplay. The popup pauses the current question timer. It does not pause the daily wall clock. Returning from instructions must resume the same question safely without charging an extra life.

English text and spoken explanations are current scope. Keep text/audio keys separate from scene layout for a later Marathi setting. The old COD narration batch must not be represented as suitable NIPUN narration without content review. Narration failure, replay timing and browser audio-unlock behavior need explicit handling and validation before the timer can be trusted.

6. Forty-minute daily limit

Use a single local anonymous profile. The initial daily allowance is a 40-minute wall-clock window from the first daily open, not forty minutes of foreground play. Instructions and pauses do not extend that window. Reset at local midnight; backend enforcement is later work.

At expiry, allow the current question to finish, then block further questions. Opening another game or restarting the browser must not grant another same-day allowance. Define and test the boundary when expiry occurs before a question starts or across midnight. Local storage is basic and cannot be described as tamper-proof or cross-device enforcement.

7. Editable Unity screens and browser target

Retain editable saved screens and named objects so the owner and another developer can change placements outside Play. Bind content and state to authored views rather than rebuilding the layout every frame. Keep NIPUN assets and screens separate from the preserved COD layouts.

Planned screen set: Home, Explore/fort route, Fort 1 game selection, stage selection, instructions overlay, MathFly, NumberLineJump, stage result/retry, game reward and daily-limit state, with settings/language-ready bindings. Exact scene/prefab paths are not yet verified and are intentionally not invented here.

Portrait browser/WebGL is the target. A working Editor scene is not proof of WebGL build success, responsive browser layout, audio autoplay compatibility or touch behavior.
